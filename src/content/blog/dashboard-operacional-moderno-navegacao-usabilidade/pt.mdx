Existe uma diferença fundamental entre um dashboard **analítico** e um
dashboard **operacional** — e confundir os dois é a origem da maioria das
telas que ninguém usa. O analítico serve para explorar dados e gerar
insights: filtros flexíveis, gráficos comparativos, exportação. O
operacional serve para **agir**: o usuário abre a tela com uma pergunta
específica na cabeça ("tem algo quebrado?", "o que eu preciso resolver
agora?") e espera a resposta em segundos.

Neste post eu destrincho a anatomia de um dashboard operacional moderno —
as peças de navegação e os padrões de usabilidade que separam uma
ferramenta que o time usa todos os dias de uma que vira aba esquecida no
navegador.

## Anatomia de um dashboard operacional

Um dashboard operacional bem construído é dividido em **camadas**, e cada
camada responde a uma pergunta diferente do usuário:

- **Contexto** — onde estou? (header, breadcrumbs, seleção de ambiente ou
  tenant)
- **Situação** — está tudo bem? (KPIs e indicadores de saúde no topo)
- **Prioridade** — o que precisa de atenção agora? (listas ordenadas por
  severidade, alertas ativos)
- **Detalhe** — por que isso aconteceu? (drill-down em uma linha, painel
  lateral, página dedicada)
- **Ação** — o que eu faço a respeito? (botões de ação contextual, links
  para o sistema de origem)

A ordem não é acidental: ela espelha o fluxo mental de quem opera um
sistema. Primeiro a pessoa se orienta, depois avalia a situação geral,
identifica o que está fora do normal, investiga a causa e age. Quando o
layout quebra essa ordem — por exemplo, colocando um gráfico de tendência
de 30 dias acima da lista de incidentes ativos — o usuário precisa
"varrer" a tela inteira a cada visita, e o custo cognitivo explode.

## Navegação: sidebar, breadcrumbs e a URL como fonte de verdade

A navegação de um dashboard operacional tem um trabalho ingrato: ser
invisível. Ninguém deveria pensar em "como navegar" — a estrutura precisa
estar onde o usuário espera que ela esteja.

### Sidebar hierárquica (e enxuta)

O padrão dominante continua sendo a sidebar à esquerda, e por um bom
motivo: ela escala verticalmente conforme o produto cresce, sem disputar
espaço horizontal com o conteúdo. Mas a regra de ouro é **profundidade
máxima de dois níveis**. Se você precisa de três níveis de menu para
organizar as telas, o problema não é o menu — é a arquitetura de
informação do produto.

```
Visão Geral
Operações
  ├── Pedidos
  ├── Entregas
  └── Estornos
Infraestrutura
  ├── Filas
  └── Jobs
Configurações
```

Agrupe por **área de responsabilidade**, não por tipo de tela. "Pedidos,
Entregas, Estornos" diz ao operador onde clicar quando o problema é X;
"Listagens, Relatórios, Gráficos" obriga ele a pensar em que formato a
resposta virá — e isso é problema seu, não dele.

### Breadcrumbs para orientação no drill-down

Conforme o usuário mergulha do KPI para a lista, da lista para o item e do
item para o log, ele precisa saber onde está e como voltar um nível.
Breadcrumbs resolvem isso de forma barata:

```
Operações / Pedidos / #48291 / Eventos
```

Uma regra importante: o breadcrumb deve refletir a **hierarquia da
informação**, não o histórico de cliques. Se o usuário chegou ao pedido
#48291 a partir de um alerta, o breadcrumb continua sendo
`Operações / Pedidos / #48291` — a posição lógica na estrutura, não o
caminho percorrido.

### A URL como fonte de verdade

O padrão mais subestimado em dashboards é tratar o estado da tela como
parte da URL. Filtros, página atual, item selecionado, intervalo de datas
— tudo isso deveria viver nos search params:

```
/operacoes/pedidos?status=falha&periodo=24h&pagina=2
```

Isso destrava três superpoderes de usabilidade:

- **Compartilhamento** — o operador cola o link no chat do time e todo
  mundo vê exatamente a mesma tela, com os mesmos filtros.
- **Histórico do navegador** — o botão "voltar" funciona como o usuário
  espera, desfazendo o último filtro em vez de expulsar ele da tela.
- **Deep-linking** — alertas enviados por e-mail ou Slack podem abrir o
  dashboard já filtrado para o contexto do incidente.

No Next.js, isso se traduz em ler os params direto na página e derivar o
estado a partir deles, em vez de manter um estado de filtro paralelo em
memória:

```tsx
export default async function PedidosPage({
  searchParams,
}: {
  searchParams: Promise<{ status?: string; periodo?: string }>;
}) {
  const { status = "todos", periodo = "24h" } = await searchParams;
  const pedidos = await listarPedidos({ status, periodo });

  return <TabelaPedidos pedidos={pedidos} />;
}
```

A mudança de filtro vira uma navegação (`router.push` com novos params),
e não uma mutação de estado local. O resultado é uma tela que se comporta
como a web espera que ela se comporte.

## Usabilidade: hierarquia, densidade e estados

Navegação leva o usuário até a tela certa; usabilidade determina se ele
consegue extrair a resposta dela. Três aspectos fazem mais diferença na
prática.

### Hierarquia visual por frequência de uso

A regra é simples de enunciar e difícil de executar: **o que é consultado
com mais frequência ocupa o espaço mais nobre** (topo, esquerda, maior
contraste). Em um dashboard operacional, isso quase sempre significa:

1. Indicadores de saúde e alertas ativos no topo.
2. A lista de trabalho (o que precisa de ação) logo abaixo.
3. Gráficos de tendência e histórico por último — eles respondem "por
   quê", não "o quê".

Um teste prático: mostre a tela por cinco segundos para alguém do time e
pergunte "está tudo bem?". Se a pessoa não conseguir responder, a
hierarquia está errada — provavelmente há um gráfico bonito disputando
atenção com a informação que realmente importa.

### Densidade de informação sem poluição

Dashboards operacionais são ferramentas de trabalho, e ferramentas de
trabalho podem (e devem) ser densas. O operador que usa a tela oito horas
por dia prefere ver vinte linhas de uma tabela sem scroll a ter um
espaçamento generoso digno de landing page. Mas densidade não é sinônimo
de poluição:

- **Progressive disclosure** — mostre o essencial na linha da tabela
  (status, id, tempo decorrido, responsável) e exponha o restante no
  hover, no expand da linha ou no painel lateral de detalhe.
- **Cor com semântica, não com decoração** — vermelho significa "precisa
  de ação", amarelo significa "observe", e nada mais deveria usar essas
  cores. Quando tudo é colorido, nada é urgente.
- **Números alinhados à direita e com a mesma precisão** — comparar
  `1.247` com `983` em colunas alinhadas à esquerda e casas decimais
  variáveis exige esforço que a interface deveria poupar.

### Os quatro estados que toda tela precisa ter

A maioria dos dashboards é desenhada apenas para o estado feliz: dados
carregados, tudo funcionando. Na prática, a tela vive alternando entre
quatro estados, e cada um precisa de um desenho explícito:

- **Loading** — skeletons no formato do conteúdo final, nunca um spinner
  centralizado que apaga a tela inteira e zera o contexto do usuário.
- **Vazio** — "Nenhum pedido com falha nas últimas 24h" é uma informação
  valiosa e deveria ser exibida com orgulho, não como uma tela em branco
  que parece bug.
- **Erro** — mensagem clara do que falhou, com ação de retry. Um
  dashboard que mostra dados parciais deve sinalizar quais blocos estão
  desatualizados, em vez de falhar em silêncio ou derrubar a tela toda.
- **Desatualizado** — dados operacionais envelhecem rápido. Mostre
  "atualizado há 2 min" e deixe o usuário confiar (ou desconfiar) do que
  está vendo.

O estado vazio merece atenção especial: num dashboard operacional, **vazio
geralmente é a boa notícia**. A tela que diz "zero incidentes ativos" de
forma clara e confiante é exatamente o que o operador quer ver às 9h da
manhã.

## Boas práticas para não construir uma tela que ninguém usa

- **Comece pelas perguntas, não pelos dados disponíveis.** Liste as
  cinco perguntas que o operador faz ao abrir a tela e desenhe para
  respondê-las nessa ordem. Métrica sem pergunta vira enfeite.
- **Um dashboard, um público.** A tela que tenta servir o operador, o
  gerente e o diretor ao mesmo tempo não serve nenhum dos três — cada um
  tem perguntas e granularidades diferentes.
- **Toda métrica exibida precisa ter uma ação associada.** Se ninguém
  faria nada de diferente ao ver o número mudar, ele não pertence ao
  dashboard operacional (talvez pertença ao analítico).
- **Preserve o contexto na navegação.** Ao voltar do detalhe para a
  lista, o usuário espera encontrar os mesmos filtros, scroll e página —
  a URL como fonte de verdade resolve isso de graça.
- **Teste com dados reais e feios.** Nomes longos, IDs gigantes, mil
  linhas, zero linhas, API lenta. O layout que só funciona com o mock do
  Figma vai quebrar no primeiro dia de produção.
- **Atalhos de teclado valem ouro para uso repetitivo.** `g p` para ir a
  Pedidos, `/` para focar a busca, `j/k` para navegar a lista. Quem usa
  a tela o dia inteiro agradece.

## Conclusão

Um dashboard operacional moderno não é uma coleção de gráficos — é uma
ferramenta de decisão com uma anatomia deliberada: contexto, situação,
prioridade, detalhe e ação, organizados na ordem em que o usuário pensa.
A navegação some de tão previsível (sidebar enxuta, breadcrumbs lógicos,
URL compartilhável), e a usabilidade respeita o tempo de quem trabalha
(hierarquia por frequência, densidade sem poluição, estados desenhados
para além do caminho feliz). Quando essas peças se encaixam, o dashboard
deixa de ser uma tela que o time consulta e vira o lugar onde o trabalho
acontece.
